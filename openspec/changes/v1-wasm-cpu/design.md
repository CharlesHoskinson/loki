# Design

## Context

See proposal.md for motivation and scope. The current repository's `Cargo.toml` already adds `getrandom` 0.2 with `js` for `wasm32-unknown-unknown` (`loki-proofs/Cargo.toml:227-229`). Rayon and BLST are regular dependencies (`Cargo.toml:154-185`), while native CUDA/build-script work is feature-gated (`Cargo.toml:48-50`; `build.rs:48-53`). Rayon-core falls back to sequential execution on wasm32; the separate worker pool must be explicitly initialized. The current W2 harness is a native binary/test harness and does not execute either prover on wasm (`loki-harness/src/lib.rs:8-11, 87-100`). The platform document still marks the WASM matrix as TODO (`docs/PLATFORMS.md:318-358`). A permitted local feasibility probe passed `CARGO_BUILD_JOBS=2 CARGO_TARGET_DIR=/home/charles/repos/loki-wt/v1/.target-luna-v1-3 cargo check --target wasm32-unknown-unknown --lib` on reference revision `eaf09d8`; this proves only that the library compiles in this environment. It does not prove browser/Node execution, threaded builds, stock-on-wasm compatibility, runtime randomness, or resource budgets.

## Goals / Non-Goals

**Goals:** Define four WASM host/mode release lanes: browser single-thread, Node single-thread, browser worker threads, and Node worker threads. Require CPU-only proof and verification behavior, stock 0.8.3 execution on wasm, portable canonical fixtures, measured resource budgets, and target-specific CI.

**Non-Goals:** Introduce a public JS package/API, change the crate's package identity or native defaults, add mobile guarantees through WASM evidence, require an accelerator, or ship WebGPU/WGSL arithmetic in v1.

## Decisions

1. **Keep browser/Node JavaScript support target-scoped.** Preserve the existing `getrandom` 0.2 `js` target dependency; test browser `crypto.getRandomValues` and the pinned Node crypto adapter. Do not enable JS glue globally because `wasm32-unknown-unknown` does not itself imply a JavaScript host. Document non-JS `wasm32-unknown-unknown` consumers as unsupported without a custom entropy integration. The caller continues to supply proof `RngCore`, as in stock; if `OsRng` host entropy is unavailable, rand_core 0.6 panics/traps rather than returning a fallible proof error. The test harness must verify no proof bundle is exported in that case.

2. **Separate the default and threaded products.** The default artifact remains a single-thread portable wasm build with no nightly atomics or shared-memory deployment requirements. A separately pinned threaded build uses Rayon with `wasm-bindgen-rayon`, atomics/shared memory, and browser cross-origin isolation; a Loki-owned Node `worker_threads` adapter must be implemented because upstream documents browser web output, not Node. Node threaded support is a concrete implementation and release-blocking runtime gate. The threaded toolchain and flags live in a dedicated build configuration and do not raise the package MSRV or affect native features. A host/mode is supported only when its complete runtime and stock-compat gates pass.

3. **Run the stock oracle on wasm as well as Loki.** Compat-proof owns `loki-harness/fixtures/v1/manifest.jsonl`, with cases carrying schema/version/source pins, fixture ID, circuit and `k`, instance/batch shape, Serde format, transcript mode, feature set, seed ID, expected outcome, transcript-vector ID, and paths plus SHA-256 digests for params/SRS, VK, PK, proof, and public inputs. It also includes wrong-input, malformed/truncated, mutated, and appended variants. Build both the path-patched Loki package and an independent exact `midnight-proofs =0.8.3` dependency for wasm. Each host/mode gate runs valid and negative fixtures through both verifiers, checks their proof/key/parameter interactions, and round-trips public `ProvingKey::bytes_length`, `write`, `read`, `to_bytes`, and `from_bytes` with stock's existing serialization (`src/plonk/mod.rs:363-431, 447-464`). Native stock verification provides an additional cross-target check. A harness may apply stronger full-input-consumption checks only where they are already part of the named compatibility contract; it must not redefine stock API behavior.

4. **Use canonical bytes, not target-native Rust objects.** Fixture inputs and outputs cross host boundaries as serialized SRS, VK, PK, proof, and public-input bytes plus circuit/config identity and expected verdicts. The compat-proof owner publishes the schema and source pin; WASM owns a runner that consumes it. Shared differential-fuzz corpus cases and Quint-owned target-neutral model traces use this same byte-oriented runner. Lean coverage remains host-side and states the wire/arithmetic contract; wasm compilation does not replace formal proof.

5. **Freeze numeric budgets from baseline measurements before candidate qualification.** `wasm:budget` reads `loki-harness/fixtures/v1/wasm-budgets.json` with pinned browser/Node version, mode, fixture ID, metric, unit, numeric limit, baseline measurement, and source revision for every lane. Required quantities are peak linear memory, `.wasm` plus JS glue size, proof bytes, and elapsed time. Perf reviews the baseline and limits; the record is frozen before a release candidate is measured, and post-freeze changes restart qualification. Record the wasm32 4 GiB address-space ceiling separately from observed host/device allocation ceilings.

6. **Measure BLST and the recursion-chain workload.** `wasm:blst-baseline` records the portable no-thread wasm32 BLST implementation against native under matched inputs, and measures SIMD128 and Rayon worker counts as separate whole-Loki configurations. `wasm:chain` must pass the small `sherlock-recursion-chain-smoke-v1` fixture on every WASM lane. Larger production-chain attempts report the measured envelope, including the largest supported size or explicit timeout/unsupported boundary; they do not turn arbitrary host limits into a universal proof guarantee. Perf owns configuration/methodology and the combined comparison table.

7. **Keep WebGPU out of the v1 CPU gate.** WASM CI runs without CUDA/WebGPU. WebGPU/WGSL field arithmetic, MSM, NTT, worker API/lifecycle integration, and associated device-loss semantics require a Loki-compatible implementation and correctness/performance evidence before entering a future change. Memory64 is also deferred; all v1 budgets are measured within wasm32's 4 GiB theoretical address space and actual host limits.

## Risks / Trade-offs

- **[BLST portable path differs in throughput or runtime behavior]** → Keep a CPU wasm build as the baseline; test actual proof and verification behavior, and record the target artifact's resource/time costs. `no-asm` is not currently a declared BLST Cargo feature in the resolved dependency; target build scripts select portable C/no-thread behavior, which must be verified rather than assumed.
- **[`loki-profile` uses unsupported host APIs]** → Add a compile-time diagnostic for `wasm32-unknown-unknown` with this opt-in feature unless `Instant` and file output receive portable backends; it is gated as a Loki-only feature in `src/lib.rs:25-26` and currently uses `std::time::Instant` and `std::fs` (`src/profile.rs:16-25, 98-115, 169`).
- **[Rayon or `std::thread` assumptions do not fit wasm hosts]** → Keep the no-thread default independent; use an explicit worker adapter and require all four runtime/mode lanes to pass before claiming support.
- **[Nightly toolchain drift breaks threaded WASM]** → Pin the exact nightly and wasm-bindgen/wasm-bindgen-rayon versions in the dedicated configuration; keep the native MSRV unchanged.
- **[Browser/Node versions impose lower memory ceilings than wasm32 permits]** → Require per-host measurements and fail closed on a missing/over-budget result.
- **[Stock crate cannot compile with the same target or feature set]** → Treat inability to compile/run exact 0.8.3 on the target as a blocking compatibility issue; do not substitute native-only stock verification.

## Migration Plan

This change adds target-specific build and test configuration without altering native defaults. Rollback disables/removes only the opt-in threaded artifact and WASM runner; stock compatibility and native behavior remain unchanged. Product documentation must list only host/mode combinations whose required gates passed at the release SHA.
