# Skew robust G1 MSM design

**Evidence convention:** unless a statement is explicitly marked **SOURCE**, **MEASURED**, **ESTIMATE**, or **OPEN QUESTION**, normative design prose in this file is **CODE (proposed contract)**. It describes required future behavior; it is not evidence that a kernel or performance result exists.

**CODE (proposed status):** implementation design for the future `loki-gpu` MSM backend. This is not a kernel result. The Rust and CUDA entry points assigned alongside this document are stubs and return `Unsupported`.

## CODE — scope and contract

The target is the BLS12-381 G1 multiscalar multiplication used by Loki's KZG commitments. The backend computes

\[
  \operatorname{MSM}(s, P) = \sum_{i=0}^{\min(|s|,|P|)-1} s_i P_i.
\]

The `min` length deliberately matches stock `msm_specific`, whose `zip` truncates mismatched slices. A caller that wants strict length checking must do so before dispatch. Zero scalars may be omitted, and an empty effective input returns the group identity. Validated resident bases are prime-order G1 points; returned points are normalized and decoded through checked BLS12-381 conversions. No Rust or CUDA struct layout casts are part of the contract.

Correctness is the gate: every returned point must equal the CPU result after normalization. This discharges only the MSM component obligation; stock-verifier acceptance still requires all other prover components, transcript order, and proof encoding to remain correct. Kernel sort order and reduction tree may differ from the CPU implementation because the group result is compared mathematically; proof emission order remains Loki's responsibility and must be unchanged.

## CODE — V1 algorithm: sorted buckets with bounded segments

Use unsigned fixed windows for the first implementation. This keeps the scalar decomposition auditable and avoids a signed-digit carry boundary.

1. **Canonical scalar words.** The Rust boundary receives valid reduced `Fq` values and serializes four little endian `u64` words in the documented sppark Montgomery wire encoding. Before digit extraction, the device converts each Montgomery value to its canonical integer representative modulo the BLS12-381 scalar modulus. The kernel then processes all 256 bits, independent of leading zeros.
2. **Fixed window decomposition.** For a selected width `w`, let `m = ceil(256 / w)` and
   `d(i,j) = (s_i >> (j*w)) & (2^w - 1)`. The top partial window is masked. Thus
   `s_i = sum_j d(i,j) * 2^(j*w)` exactly; there is no carry or discarded top window. Emit one `(key=(j,d), value=i)` record for each nonzero digit. A zero scalar emits no records. An identity base is allowed and contributes the identity.
3. **Radix sort and run metadata.** Sort records by `(window,digit)` using a stable device radix sort. Run length encoding produces each nonempty bucket's start and count; a prefix scan produces offsets. Keys and counts stay on device. Launch extents use checked upper bounds, so the device does not synchronously read bucket counts back to the host.
4. **Bounded bucket work.** Partition each bucket's half-open sorted range `[start,start+count)` into contiguous segments of at most `L` points. Each segment is summed using a balanced block reduction into one partial. A bucket with `q` entries therefore creates `ceil(q/L)` partials; no worker receives an unbounded serial chain. Segment boundaries are disjoint and cover the bucket exactly once.
5. **Deterministic segmented fold.** Reduce each bucket's partials with a fixed pairwise tree until one projective bucket sum remains. Missing buckets are the identity. This reduction is deterministic for a given input and launch configuration, and the group result is independent of the chosen tree.
6. **Window reduction.** For each window, compute `sum_{d=1}^{2^w-1} d * B[j,d]`, where `B[j,d]` is the bucket sum. Use the standard reverse running-sum identity: visit digits high to low, add the bucket to a running sum and add the running sum to the window sum. This gives the weighted sum without an independent scalar multiplication per bucket. If the digit range is divided into chunks `[a,b]`, the local reverse sum has coefficient `(d-a+1)` on `B[j,d]`; add `(a-1) * sum_{d=a}^b B[j,d]` to recover the global coefficient `d` before combining chunk results.
7. **Window combination.** Initialize the accumulator with the top window sum, then visit lower windows high to low, doubling the accumulator `w` times before adding each next window sum. The top window is partial when 256 is not divisible by `w`; it is not shifted before initialization. Include it in the result. Normalize once at the end, return one G1 result, and validate the returned encoding before exposing it to Loki.

The segment kernel has a hard per-worker bound `L`; sort and RLE work scales with the number of nonzero digits, not with the size of the largest bucket's serial dependency chain. Degenerate cases have direct meanings: all-zero scalars create no records and return identity; one repeated scalar creates large but well-segmented bucket runs; boolean inputs create at most two nonzero digit values per window; random scalars exercise the ordinary many-bucket case.

### ESTIMATE — width, segment size, and work bounds

Do not inherit a window width or thread count from another GPU. For `n` effective points and `m` windows, the maximum record count is `n*m`; use checked arithmetic before allocating. At `n=2^20` and `w=12`, `m=22`, so the record bound is about 23.1 million entries. A packed 32-bit key plus 32-bit point index is about 176 MiB before sort temporary storage, bucket metadata and partial sums. This estimate is planning arithmetic, not a measured peak.

The first tuning sweep should test a small set of legal widths (8 through 16, subject to the scratch budget) and `L` values (64, 128, 256). Select by end-to-end backend wall time on sm_120, including conversion, allocation, sort, transfer and final normalization. **ESTIMATE (initial admission policy):** reserve 2 GiB for runtime and other proof state until full k19/k20 allocation traces replace this conservative starting assumption. If worst-case scratch does not fit, process the batch in smaller groups or use the fallback before starting; never partially dispatch and then silently report success.

### OPEN QUESTION — optional low-cardinality specialization

A later specialization may group identical scalar values, sum the corresponding points with a segmented reduction, and run the bucket MSM on the resulting distinct `(scalar, point-sum)` pairs. Its identity is

`sum_i s_i P_i = sum_{u in distinct(s)} u * sum_{i:s_i=u} P_i`.

This can reduce work for repeated values, but adds a full-width scalar sort or an equivalent exact grouping pass. It is not required for V1. Consider it only if the segmented bucket implementation misses the structured-scalar gate and an inexpensive probe can select it without slowing random inputs. The decision is performance-only: both routes must satisfy the same differential contract.

## CODE (proposed) — resident bases, precomputation, and batching

The SRS is fixed across many commitments. The backend API should accept an opaque, validated resident-base handle and a requested prefix length, not force each call to upload a new `Vec<G1Affine>`. The registry owns the validated source snapshot and handle; it must check the exact consumed prefix on a cache hit, including after source mutation or pointer reuse. **CODE:** Loki's current legacy CUDA cache uses two entries and synchronous sppark calls. **CODE (proposed):** W13's in-flight SRS registry replaces that policy with budgeted prefix reuse; it is not yet a measured concurrency result and is not part of this module's implementation.

An optional fixed-base table may split `m` scalar windows into `p` contiguous groups of `q=ceil(m/p)` windows. Store `P[i,j]=2^(w*q*j)P[i]` for base `i` and group `j`. For each local window `k<q` with `j*q+k<m`, bucket `P[i,j]` using the scalar digit at original window `j*q+k`, reduce that local window normally, and combine the `p*q` contributions; padded local windows with `j*q+k≥m` have no terms. The identity follows from `2^(w*(j*q+k))=2^(w*k)2^(w*q*j)`. This trades about `p` times base storage and more points per local bucket for fewer serial window-reduction rounds; it does not reduce the total scalar digits. It is deferred to P9 after the sorted-bucket path has exact differentials. Build it only from a validated immutable base snapshot, account its full memory in the resident budget, and verify each table entry against the defining group multiple. Give it a separate proof test and cold/warm amortization benchmark; keep it disabled unless it meets P9's ≥10% throughput target with p95 single-chain latency regression no worse than 5%. Do not make precomputation a correctness prerequisite or let table construction mutate the original base handle.

The API exposes `MsmBackend::msm_batch` and `SrsRegistry::srs_msm_batch` over shared bases; the default implementation delegates to single MSM calls sequentially and publishes the ordered result vector only if all calls succeed. **CODE:** This is the required V1 batch contract. A GPU override may batch transfers/launches while preserving request-slot order and all-or-error output publication. Each vector retains independent key/segment state; batch identifiers must be included in keys if records are combined into one sort. An implementation may instead issue grouped launches over per-vector scratch when that uses less memory. Results must not be reordered by stream completion. Batch admission is limited by the estimated record and sort scratch footprint and the global device budget; begin with sequentially completed batches until overlap is measured. This module does not schedule proof dependencies or change transcript absorption order.

The public V1 API blocks until a call has retired; any CUDA streams/events remain internal. Internal queued work must retain its resident handle, scalar staging memory and unpublished output storage until the completion event. On any error, inputs remain unchanged, no partial result is published, and temporary outputs are discarded. The dispatcher owns sticky backend disable and CPU fallback. It must only retry from preserved host inputs and emit commitments in the original Loki order.

## CODE — Rust/CUDA boundary

The assigned V1 FFI name is `loki_gpu_msm_v1` in `cuda/include/loki_gpu_ffi.h`, with status codes `OK=0`, `UNSUPPORTED=1`, `INVALID_ARGUMENT=2`, and `RUNTIME_ERROR=3`. Its byte layout is documented by the Rust MSM module: scalar records are 4 little endian `u64` words; affine G1 records are `x[6] || y[6]` little endian `u64` limbs in the selected Montgomery wire representation; identity is `(0,0)`; output uses the same affine layout. No Rust type is transmuted to the wire representation.

The current entry point is a synchronous host-byte ABI and returns `UNSUPPORTED` before reading inputs or writing output. It is only a compile-time seam. The API's public `SrsLease`/`ResidentBuffer` metadata must first be validated against the backend-owned generation and allocation registry. A production MSM then needs a private resident path to the kernel: either a versioned FFI receiving the validated native allocation handle/pointer, requested prefix, scalar source, output destination and stream/context, or a private Rust-to-kernel wrapper that resolves the same registry entry. The public API stays blocking in V1, so this path must wait for completion and publish a fresh host result only after success; it must not copy the resident bases through host bytes for each MSM. Caller-supplied allocation IDs are never trusted as pointers, and a host pointer must never be treated as a device pointer implicitly.

The CUDA implementation should use sppark's Apache-2.0 BLS12-381 field and curve primitives rather than reimplementing those arithmetic layers. Keep this algorithm in separate kernels; do not patch sppark's cooperative Pippenger kernel. A device fault must not trigger destruction of resident handles through a poisoned CUDA context; the API/runtime layer owns that recovery policy.

## CODE (proposed) — work package for implementation

**Owner role:** GPU MSM implementer. **Files:** `crates/loki-gpu/src/msm.rs`, `crates/loki-gpu/cuda/msm.cu`, new differential test/benchmark files, Loki `src/backend/dispatch.rs`, and Lean `LokiLean/BackendMsm.lean`. **Feature:** `cuda-msm-balanced`, dependent on the runtime, SRS registry and explicit `loki-gpu-backend` selection; the default backend remains stock CPU. The crate's `cuda` feature controls native compilation. Preserve legacy feature meanings: `cuda-srs-registry` implies legacy `cuda`, and `cuda-argument-commit` remains the compatibility alias for backend-neutral `loki-argument-commit`. The new path uses `loki-gpu-srs-registry`; reject selecting the new backend alongside any direct legacy `cuda` or `cuda-ntt` flag. **Dependencies:** P2 runtime, P3 validated SRS registry, stable backend API, and a measured remaining-work admission profile after W10. The host-byte v1 stub can land before those dependencies.

**Effort estimate:** 1–2 engineer-days for the Unsupported seam, conversion specification and direct harness wiring; 5–8 additional engineer-days for the V1 sort/segment/window kernels, adversarial differential coverage and sm_120 tuning. This estimate excludes resident ABI v2, fixed-base tables and full recursion-chain integration; it is planning only, not measured implementation effort.

1. Land the Unsupported ABI stubs and exact wire conversion first. Reject invalid byte lengths before any native call. The unsupported implementation returns no output and leaves caller-owned bytes unchanged.
2. Add a direct kernel differential harness that calls the GPU implementation without fallback. Compare normalized GPU results with CPU for random, all-zero, all-one, boolean, alternating, repeated `0..15`, one repeated full-width value, `r-1`, high-window-only values, identity bases, cancellation pairs, and 99%-dominant values. Include lengths `2^k-1`, `2^k`, `2^k+1`, empty and mismatched inputs (the latter must obey the documented zip rule).
3. Prove/check scalar decomposition, zero filtering, exact once-only index coverage, segment partition coverage, bucket concatenation, and group result equality in Lean. Link the tests to the backend MSM obligations; no random-only gate is sufficient.
4. Run at least 10,000 small differential cases against both CPU and sppark, then k16/k18/k20 structured-scalar runs with at least three samples per mode. Record GPU dispatch counts so fallback cannot hide failures.
5. Run W2 through `loki-harness` with P6's explicit `loki-gpu-backend` and `cuda-msm-balanced` feature forwarding (the new flags must be wired by P6; `loki-gpu`'s `cuda` feature enables native compilation). Require the unmodified stock 0.8.3 verifier to accept output proofs, then benchmark the complete Sherlock leaf → parent → decider chain at k19/k20 with keys and host conditions pinned. Attribute create_proof and outside-proof latency separately.

**ESTIMATE / future promotion gate:** first measure the remaining eligible full-call MSM time with W10 coefficient commitments fixed; defer this performance scope if the aggregate cannot plausibly clear 3% of the contemporaneous whole-proof window. That budget is necessary, not the amount the kernel can remove. For each structured scalar family, target a median backend wall time at most 1.2 times the random-scalar median; target random-scalar median at most 1.1 times sppark; require zero fallbacks and every stock-verifier gate. Promotion requires a measured ≥3% reduction in a matched whole-proof or complete-chain median. Historical W10 A3 was 175.256 s prove-plus-verify, so 3% on that historical denominator is 5.258 s; it is not the current baseline. **ESTIMATE:** a rough phase decomposition suggested about 2.4 s of the 85.91 s `create_proof` may be associated with advice-commitment skew, but that is not a hard bound and the skew/cache split is unknown. The 43–61 s historical regression class was in lookup/permutation argument commitments and was addressed by W10's coefficient-basis strategy; do not count that old regression as a new gain. Kernel robustness remains useful as a regression guard even if the standalone speed package fails this whole-proof admission gate.

**Kill criteria:** stop the standalone balanced MSM package if random calls exceed 1.1 times sppark after tuning, any structured family exceeds 1.2 times random, worst-case scratch cannot fit within the reserved budget, exact differentials fail, or the stock verifier rejects. Reassess only if a distinct production Lagrange-basis path shows enough measured chain latency to justify it. No kernel microbenchmark is a chain speedup claim.
