# luna-r2 review: cryptographer lens

## Concerns

- `docs/ARCHITECTURE.md:3,29,172-174` and `docs/diagrams/platforms.svg:3,16,27` state that acceptance is "the one contract every Loki build keeps," that every proof keeps the same transcript/encoding, and that stock "accepts every proof." This is broader than the evidence and contradicts the documented mixed committed/plain multi-proof case where stock rejects its own proof (`docs/modules/plonk.md:43`; `LOKI-QUINT.md:120-165`). Most compatibility evidence is specific: W2 covers synthetic k10/k14/k17 proofs with stock 0.8.3; the harness also records lookup byte differences from stock. **Suggestion:** scope these statements and the platform diagram to the tested supported inputs/configurations; keep the stock defect visible beside the general contract. The `correctness.svg:27-29` center caption should use the same scope.

- `README.md:21,32,151` says "The proof does not change," calls the contract that "the proof the stock verifier sees is the proof stock would have made," and says circuits, keys, and transcript order remain stock. This overstates the evidence. The docs describe deterministic leftover lookup placement in Loki and randomized `HashMap` iteration in stock, so fixed-RNG lookup proofs can differ; the W2 harness records lookup proofs first differing at byte 192 (`loki-harness/README.md:25,89-96`). Current Loki main `a256a9a` restores stock `HashMap` traversal by default; `loki-deterministic-lookup-order` sorts leftovers only when enabled. Separate runs can still differ in lookup bytes because the default map iteration is randomized. Mixed committed/plain instances across multiple proofs also have a stock prover/verifier absorption-order defect; `docs/modules/plonk.md:43`, `LOKI-QUINT.md:120-165`, and `src/plonk/prover.rs:467-494` versus `src/plonk/verifier.rs:63-75` document and reproduce it. The supported claim is verifier compatibility for exercised supported cases, not universal proof-byte equality or acceptance for every API shape. **Suggestion:** state the contract as "for tested supported inputs/configurations, Loki proofs are accepted by the unmodified stock verifier"; scope byte equality to matching seeds, worker settings, and circuit cases where measurements show it. Link the known multi-proof instance limitation next to the contract.

- `docs/ARCHITECTURE.md:195-203` says `lokiMainBackend_refines` "assembles Loki main's backend and discharges both conditions." That is too strong for the Lean artifact described in the neighboring lines: `loki_proof_eq_stock` is over an abstract shared `prove` program under `Refines`/`SameOrder`, equal inputs, randomness/thread count, and fixed map order (`loki-lean/LokiLean/Refinement.lean:833-858`). The main backend theorem leaves `quot` as a parameter (`Refinement.lean:1179-1197`); connecting quotient results to the proof has the separate `OBLIGATION(quot-inputs)` (`:1101-1121`), and the spec lists `stock-trace-faithful` and `keygen-deterministic` as open (`SPEC.md`). The model also does not wire stateful W9 MSM behavior into the assembled backend (`Refinement.lean:1142-1148`). Architecture line 202 itself says the Lean spec is behind main. **Suggestion:** say the Lean theorem proves a conditional abstract result and list which obligations remain for deployed Rust/CUDA; do not say it discharges the concrete backend refinement.

- `docs/modules/transcript.md:5,20,24-27` describes matching transcript sequences as the compatibility contract, says the transcript files are identical to registry source, and lists an event schedule. The page does mention the multi-circuit committed-instance difference at line 25, but it does not say that stock rejects its own proofs for mixed committed/plain columns with multiple proofs, nor scope the general statement at line 5. The concrete implementation loops differ: Loki prover absorbs committed and plain columns per proof (`src/plonk/prover.rs:467-494`); verifier absorbs all committed commitments before plain values (`src/plonk/verifier.rs:63-75`). The issue is independently recorded as a passing diagnostic that observes stock rejection (`LOKI-QUINT.md:161-165`). **Suggestion:** add the exact triggering shape and the tested limitation to the transcript page; qualify the transcript compatibility statement. Also clarify that the listed sequence abstracts per-proof instance ordering and does not imply equality on the known mixed batch case.

- `docs/modules/poly-multiopen.md:25` says feature-enabled proof bytes equal the serial path at the same seed and worker count. The evidence is narrower: the note reports eight before/after byte-identical pairs on k16/k17 synthetic `ProfileCircuit` runs with fixed worker counts (`LOKI-MULTIOPEN.md:145-154`), then says byte identity across thread counts, k20, recursive-parent, and GPU is not claimed (`LOKI-MULTIOPEN.md:170-176`). This equality is Loki-serial versus Loki-feature, not equality to registry stock: W2 lookup proof bytes differ from stock at offset 192 due to stock's randomized lookup map (`LOKI-MULTIOPEN.md:180-188,518-523`). **Suggestion:** say the feature matched serial Loki bytes in the recorded k16/k17 runs at 4 and 20 Rayon threads, and link the note; explicitly distinguish that from stock cross-verifier acceptance.

- `docs/modules/poly-multiopen.md:15` says parallelism applies only when there is more than one set and at least 4096 input coefficients. That describes the independent-set division in `prepare`, but not the entire module: `combine` parallelizes disjoint coefficient chunks whenever the first polynomial has at least `PARALLEL_THRESHOLD` coefficients, even with one polynomial/set (`src/poly/kzg/multiopen.rs:57-93`). **Suggestion:** distinguish the `combine` coefficient threshold from the multi-set root-division path's condition.

- `README.md:154` says the Lean theorem is conditional on a backend refining stock operations in the same order and that runtime checks do not complete proofs. The conditions are more specific: `loki_proof_eq_stock` is a theorem over the shared abstract `prove` function and requires `Refines`, `SameOrder`, equal inputs, equal `i.rnd`/`i.threads`, and a fixed map order `ord` (`loki-lean/LokiLean/Refinement.lean:833-858`). It does not verify the deployed Rust/CUDA implementation. The quotient-kernel connection is separately conditional on `OBLIGATION(quot-inputs)` (`Refinement.lean:840-843,1104-1122`), and `lokiMainBackend_refines` composes only listed component obligations. W2 fixtures remain synthetic and cover k10/k14/k17 by default (`loki-harness/README.md:30-46,89-96`); GPU stock-acceptance checks are one host and specified circuits (`docs/GPU.md:315-336`). **Suggestion:** call it a conditional abstract refinement theorem and state the equal-randomness, thread-count, and map-order assumptions. Describe Rust/CUDA tests as empirical component evidence; do not imply the theorem machine-checks the deployed implementation.

- `README.md:156` says mutated witnesses "must be rejected by both." W7 does not assert unconditional rejection for an arbitrary single-cell mutation: it first asks Loki and stock `MockProver` whether the mutant satisfies constraints; if MockProver accepts it, both verifiers must accept the proofs, and if MockProver rejects it, both must reject (`LOKI-FUZZ.md:60-66`). W7 also records that proof-roundtrip and soundness fuzz inputs stayed at 4-6 bytes and so the campaigns were close to seeded random testing, not structured-byte mutation (`LOKI-FUZZ.md:105-109`). **Suggestion:** say the negative controls that MockProver deems invalid and the corrupted proof/input/VK cases are rejected, and include the campaign-generation limitation when presenting the fuzz result as soundness evidence.

- `docs/ARCHITECTURE.md:227` has the same ambiguity in its W7 table: it lists mutated witnesses among cases that any acceptance would make release-blocking, without explaining the MockProver positive control. `LOKI-FUZZ.md:60-66` says a satisfying mutant is expected to pass both verifiers. **Suggestion:** clarify that only mutations the constraint oracle rejects count as invalid witness cases.

- `README.md:38` points readers to `LOKI-DONE.md` for a G2 that names k20 and stock 0.8.1, but the linked harness evidence says its ordinary gate is k10/k14/k17, k20 is ignored by default, and its registry oracle is 0.8.3 (`loki-harness/README.md:21-28,89-96`). A search of the assigned docs found no 0.8.1 verifier run or k20 cross-verification result. `LOKI-DONE.md:9` is phrased as a gate definition, not a completed result, but the README cross-reference can be read as validation evidence. **Suggestion:** label G2's k20 and 0.8.1 cases as pending until there is a command and recorded result, or link the missing evidence.

- `docs/ARCHITECTURE.md:48,208-219` said all four Quint models had Rust replay tests that drive real code. The scheduler is only a proposal, and `quint/mbt/README.md:63` says there is no scheduler implementation to replay. The architecture text now distinguishes the three replayed models from the scheduler proposal.

## Questions

- Which API shapes count as supported for the headline stock-verifier acceptance claim, given the known mixed committed/plain multi-proof shape where stock rejects its own proof?
- Should the README's "same proof" brand line refer to verifier-compatible proof semantics, or is byte identity intended for a narrower set of controlled executions?

## Suggestions

- Put the distinction between (a) proof-byte equality, (b) cross-verifier acceptance, and (c) transcript-event equality in one short terminology note linked from README and the transcript/multiopen module pages.
- Scope the universal-sounding "every build" statement in `README.md:21` to configurations actually covered by the tests. The stock-verifier evidence itself is version- and fixture-specific (0.8.3; GPU-specific evidence also names circuit/size and host).

## Novelty evidence

- The root-product division at `docs/modules/poly-multiopen.md:13,19` is already attributed to midnight-zk PR #565. The [primary PR page](https://github.com/midnightntwrk/midnight-zk/pull/565) says KZG multi-open divides by the product of `(X - point)` and skips zero coefficients. That is prior art against claiming the general root-product division idea as novel. Loki's supported contribution is its prover integration, preserved stock verifier source, measured CPU speedup, and recorded Loki-serial/feature byte equality on specified k16/k17 runs.
- `LOKI-MULTIOPEN.md:22-25` also cites `axiom-crypto/halo2` PR #37 as a precedent. The [primary PR page](https://github.com/axiom-crypto/halo2/pull/37) describes parallelizing `compute_inner_product` for large vectors; it does not describe root-product division. Correct or remove this citation unless a different PR #37 was intended. The note also names a supplied `other-chains-plonk-kzg.md` research document; cite its underlying paper/primary source before using it to establish novelty or precedent.
