## Outside best practice (primary sources)

- Lean Reference, validating a proof: <https://lean-lang.org/doc/reference/latest/ValidatingProofs/>. It explains transitive `#print axioms` output, says `sorryAx` means an incomplete proof, and distinguishes the standard `propext`, `Classical.choice`, and `Quot.sound` axioms from custom assumptions. It recommends `lean4checker` in CI. For Loki, pair independent checking with an explicit allowlist-based audit and preserve named theorem reports; neither source-text grep nor a green `lake build` is a sufficient trust check.
- Lean Reference, axioms: <https://lean-lang.org/doc/reference/latest/Axioms>. It documents standard axioms and explains that native evaluation introduces separate axioms tied to compiler correctness. Do not silently treat `native_decide`/native-evaluation trust as equivalent to the standard set.
- Mathlib project setup: <https://leanprover-community.github.io/install/project.html>. Lean projects pin toolchain/dependency versions and use Lake to build/cache. Loki already pins Lean/mathlib versions (`lean-toolchain:1`, `lakefile.toml:12-18`); CI should consume those pins and record them with the exact source SHA.
- Mathlib contributor guidance: <https://leanprover-community.github.io/contribute/how-to-contribute.html>. Recommends `lake build` before submitting changes. For Loki this is one gate among proof-holes, axiom, Rust-drift, compatibility and target QA checks.
- `axiom-audit`: <https://github.com/leanprover-community/axiom-audit>. The scout fetched its README and reports it audits kernel environment transitive axioms against an allowlist, catching `sorryAx`, `native_decide` dependencies and custom axioms that grep misses. A compatible version should be pinned/evaluated on Lean v4.34.1 before adoption; otherwise keep the existing `AxiomSweep` and enforce it in CI.
- Lean4 reference-manual CI workflow: <https://github.com/leanprover/reference-manual/blob/main/.github/workflows/ci.yml>. It demonstrates CI building and publishing generated artifacts. For Loki, archive machine-readable build/drift/audit outputs as release evidence tied to the tested commit rather than only keeping a mutable summary page.
