# REVIEW v1-wasm-cpu (haiku-v1-3)

`openspec validate v1-wasm-cpu --strict` -> "Change 'v1-wasm-cpu' is valid". Every requirement in specs/wasm-cpu/spec.md has at least one WHEN/THEN scenario. Findings are about content, not format.

1. [BLOCKER, spec vs code] Entropy "fail closed ... returns an error and emits no proof" (spec.md:21, tasks 1.4). rand_core 0.6.4 `OsRng::fill_bytes` panics on error (`~/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/rand_core-0.6.4/src/os.rs:58-65`), and `ParamsKZG::unsafe_setup(k, OsRng)` (`src/poly/kzg/mod.rs:70`) takes that path. The requirement needs either a fallible RNG entry point or the scenario must say "panics before any output is written" and the test must assert that.
2. [FIX, anchor wrong] spec.md:46 cites `loki-harness/src/lib.rs:22-29` as the budget anchor. Those lines are the `Metrics` struct (k, keygen_s, prove_s, verify_s, proof_bytes), not a budget. No budget record exists yet. Name the intended budget file path.
3. [FIX, anchor loose] spec.md:35 and tasks 1.1 cite `src/plonk/mod.rs:363-431` for PK interchange. Real PK methods are at `src/plonk/mod.rs:387` (write), `:409` (read), `:447` (to_bytes), `:454` (from_bytes). `bytes_length` at `:223` must be checked for the owning type before it is cited. Also `loki-proofs/...` prefixes should be repo-relative paths in the worktree.
4. [GAP, missing requirement] R1 from my inventory: `loki-gpu-backend` and `loki-sppark` (`Cargo.toml:64-73`) pull `cuda` with no target gate, and `cargo check --target wasm32-unknown-unknown --lib --features loki-gpu-backend` fails in the nvcc build script (`loki-gpu/crates/loki-gpu/build.rs`). spec.md:75 says CPU gates "SHALL NOT require CUDA" but says nothing about the wasm build with GPU features. Add a scenario that the wasm32 target rejects GPU features cleanly (cfg or compile_error), with a verification command.
5. [GAP, documented not enforced] spec.md:90 states `loki-profile` is unsupported on WASM, but only as documentation. `src/profile.rs:24,131,164` calls `Instant::now()`, which panics on wasm32-unknown-unknown (std source `library/std/src/sys/time/mod.rs` falls through to `unsupported.rs`, which panics). Require a compile-time guard (`compile_error!` under `cfg(all(target_arch="wasm32", feature="loki-profile"))`) or a portable clock, not only prose.
6. [FIX, technically wrong] spec.md:61-65 and tasks 3.2 ask for a BLST "threaded" mode and a "SIMD128" mode. On wasm32, blst's build.rs forces `no-threads` and compiles portable C with `-ffreestanding` (`blst-0.3.17/build.rs:47-53, 223-226`), so BLST has no threaded mode. Threads come from rayon. SIMD128 only changes codegen for Rust limb code, not BLST's C path (docs/PLATFORMS.md:324). Rewrite as: BLST portable path, plus the whole-Loki build with and without `+simd128`, plus rayon thread count.
7. [GAP, dependency not defined] spec.md:67-72 and tasks 3.3 require "the compat-proof-owned recursion-chain fixture". No such fixture exists in the worktree (`loki-harness/src/lib.rs` has only k=10/14/17/20 compare; no chain runner). Name the fixture ID and its owner's file, or mark it blocked.
8. [GAP, testability] Requirements at spec.md:16-21 and 45-58 say "pinned supported browser and Node runtime" and "frozen numeric limit" without naming versions or numbers. Tasks 3.1 says "Do not fill limits from estimates", which is right, but the spec needs a named record path and a schema so `wasm:budget` can fail closed on a specific file.
9. [RISK, not captured] `getrandom` 0.2 `js` is enabled in library code for all wasm32-unknown-unknown consumers (`Cargo.toml:227-229`). The getrandom 0.2 README (tag v0.2.17) warns against enabling `js` in libraries because it breaks non-web wasm builds and bloats Cargo.lock. The design (design.md:15) keeps it target-scoped, which is better, but the spec should require that a non-web wasm consumer (wasi-like or no-js) still builds, or that the js dependency is made opt-in.
10. [RISK, upstream fact] wasm-bindgen-rayon's README (`https://github.com/RReverser/wasm-bindgen-rayon`) requires `--target web`. design.md:17 already says Node needs a Loki-owned worker adapter. Keep that line in spec.md scenario 2.2 ("the pinned Node worker adapter") and say it is Loki-owned, not upstream.
11. [OK] Strict validation passes. Scenarios name host, mode, fixture and verdict. The "frozen"/"pinned" wording is unresolved until release candidate freeze (already in design.md:9 and tasks 4.1).

Verified in this review: `cargo check --target wasm32-unknown-unknown --lib` passes for default features (inventory.md section 1); `tests-stock` with unmodified midnight-proofs 0.8.3 passes `cargo check --target wasm32-unknown-unknown --tests` (inventory.md section 9). Not verified: any wasm execution, any threaded build, any budget.
